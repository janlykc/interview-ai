One clarification affects the architecture: when you say “act in an NLB,” do you mean a service behind a Network Load Balancer? If so, we need to establish where HTTP requests and authenticated tenant identities become visible.

For a concrete example, suppose tenant A has a sustained allowance of 100 requests/second, can burst to 200 requests, and also needs limits per client. Those numbers are illustrative.

The rate-limit key could be:

(tenant_id, client_id, policy_scope)

Here:
- tenant_id comes from a trusted identity, such as validated authentication.
- client_id could identify an API credential, application, or authenticated user.
- policy_scope identifies a shared quota or an endpoint group, such as “writes.”

Source IP can be useful for anonymous traffic or abuse protection, but shared NATs mean it often represents many clients. We should clarify what “source” means before choosing the key. A request might need to pass both a tenant-wide limit and a client-specific limit.

The main algorithm choices are:

Technique | Behavior | Bursts | Main tradeoff
Fixed window counter | Counts requests in each fixed interval | Can admit nearly twice the limit across an interval boundary | Simple and small state, but uneven enforcement
Sliding window log | Tracks request timestamps over the preceding interval | Enforces an exact rolling quota | State grows with request volume
Sliding window counter | Approximates a rolling quota using adjacent counters | Reduces fixed-window boundary spikes | Small state, but approximate
Token bucket | Tokens refill at a steady rate; requests consume tokens | Allows a bounded burst up to bucket capacity | Good fit for sustained rate plus burst allowance
Leaky bucket | Queues and drains work at a steady rate, or uses equivalent admission accounting | Queuing can absorb bursts and smooth output | Adds latency; queue capacity and overflow behavior matter

For our example, token bucket is a useful starting candidate:

refill rate = 100 tokens/second
capacity = 200 tokens
request cost = 1 token

An idle client can send 200 requests immediately. Once those tokens are consumed, it earns another 100 per second. Under persistent overload, excess requests are rejected unless we explicitly choose to queue them.

That leads to an important distinction: do we want to reject excess traffic, or delay it? A decision library can return an allow/deny result and retry information. Delaying requests requires the traffic-handling service to own a bounded queue and its latency behavior.

Before choosing the algorithm, I’d clarify these requirements with the interviewer:
1. Is this HTTP request limiting behind an NLB, or connection-level limiting?
2. Does “source” mean tenant, API key, user, IP address, or a combination?
3. Should limits be globally enforced across service instances, and how much temporary overshoot is acceptable?
4. Should excess requests be rejected immediately or queued?
5. Do policies require a sustained rate with bursts, an exact rolling quota, or both?

My provisional preference is token bucket for burst-plus-sustained limits, with a separate rolling quota if the contract requires something like “at most 10,000 requests in any preceding hour.” Does that match the traffic behavior you’re being asked to support?

Let’s lock in token bucket. Its two independent controls fit the requirement:
- Capacity B: maximum burst allowance.
- Refill rate r: sustained request rate.

Its main advantages are bounded bursts, constant-size state per rate-limit key, and support for weighted requests—for example, an expensive request consuming five tokens.

The main limitations are:
- It permits an immediate burst, so the downstream service must tolerate that burst.
- It limits admissions, not concurrent work. Slow requests can still accumulate.
- It doesn’t enforce an exact rolling-window quota.
- Across multiple service instances, shared bucket updates need atomic coordination; that accounting can become a bottleneck.

We don’t need a background process continuously filling buckets. We can refill lazily when a request arrives:

elapsed = now - last_refill
available = min(capacity, tokens + elapsed × refill_rate)

if available >= request_cost:
    allow
    tokens = available - request_cost
else:
    deny
    tokens = available

last_refill = now

This takes O(1) computation and state per active bucket. Idle clients cause no refill work. Fractional tokens—or fixed-point arithmetic—avoid losing partial refill credit.

For example, with capacity 200 and refill rate 100/second, a client that exhausts its bucket and returns after 0.25 seconds has earned 25 tokens. We calculate that on arrival; no timer ran in between.

The remaining accounting question is where that state lives:

State location | Benefit | Cost
In each service instance | Fast local decisions | Independent buckets multiply the effective allowance
Shared authoritative store | Consistent tenant-wide allowance | Network call and atomic update per decision; hot tenants can contend
Central allocator with local token leases | Most decisions happen locally | More complexity; allocation can strand capacity and must bound outstanding grants

My recommendation is to start with lazy refill and atomic shared decisions as the correctness baseline. If the required throughput makes shared accounting too expensive, we can introduce bounded local token leases.

That separates two concerns: refilling is cheap arithmetic; distributed coordination is the potential bottleneck.
